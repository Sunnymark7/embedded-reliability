# 任务 Playbook

借鉴 Impeccable 的按意图路由、上下文发现与编辑前质量底线；本实现独立编写，无前端/视觉步骤依赖。

## init / design

从当前工程与用户要求提取 profile、硬件完整型号、板级来源、内核/SDK/编译器和接口证据；未获硬件仍可完成纯逻辑设计，未知项保留。使用必要的项目配置/模块契约模板，不强制生成一堆空文件。`init` 只写用户要求的项目规范，`design` 默认交付设计，均不暗中改功能实现。

设计至少解释依赖方向、IRQ/任务/DMA/其他核的访问者、资源和时间上界、完成与取消、失败与恢复。迁移不要靠一张型号名列表，使用型号审查入口的差异证据表。

## build / harden

1. 读取 context、目标系列和当前领域参考；编辑前读底线。
2. 对比当前行为和验收目标，复用本地接口/驱动；只修改已授权范围。
3. 先把输入、对象寿命、回调/锁、总时限和错误契约变清楚，再实现。不能以强转、禁告警、乱加 volatile 或增延时掩盖根因。
4. 跑相关构建/测试。编辑后 hook 若未被宿主确认运行，手动 `detect` 相关文件一次；对 finding 判断真实缺陷、已有检查/有依据例外、或尚未确定。必要修复不受“只检查一遍”限制。
5. 交付实际证据与缺口，用户未请求时不持续扩展架构或风格打磨。

## audit / port

`audit` 只读。每项包含位置、场景、后果、依据、建议与验证；检查清单未勾选不是已发现 bug。

`port` 含实际迁移请求时可实施，只有“评估能否移植”则只读。先记录 source→target 的 ABI/字节宽度、内核、IRQ/RTOS port、时钟、pinmux、电气、DMA/缓存/内存域、启动/Flash、安全域、外设语义和 errata 差异；通用 core 可独立验证，硬件路径等待必要证据。不从“引脚兼容”推导软件/电气兼容。

## detect / doctor

都只读：`detect` 检查明确文件中的少量机械风险线索；`doctor` 列出配置、型号来源、扫描截断与验证缺口。二者不执行项目任意构建命令、不自动修复/生成 profile、不触发设备操作。

模型解释代码与手册的任务不能由正则扫描替代；带 `--strict` 的检测只把明确禁用函数信号作为 CLI 失败，review finding 仍需判断。
