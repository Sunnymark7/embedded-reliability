# AI 辅助开发的任务契约

目标是减少模型猜测、跨层误改和无证据完成；不把每次小修都扩展成大型架构流程。

默认采用 [适度设计](proportionate-design.md)。写代码以简单、符合项目嵌入式规范、合理注释和可维护为目标；不要因技能清单给每层加判空、长度验证、锁、重试/状态机。保证真实边界正确，复用内部契约；超出任务所需的额外保护先提出具体方案与代价供用户选择。没有明确成本/范围变化时不反复提问。

## 给 AI 的输入

尽量从仓库提取而不是反复采访用户：当前需求/可观察验收条件；允许修改的组件；目标 profile；目标工具链/SDK/内核 commit；同类实现；硬件手册/勘误修订；接口/协议；可用构建、测试与硬件。必要事实不明时标 `unknown`；只暂停依赖该事实的实现。

`AI-01` 必须：硬件相关代码的依据可追溯到本地头文件/同版本源码或官方手册。不得编造 API、寄存器地址、位值、引脚复用、缓冲大小、cache line 或 timeout 参数。公开文档只能补充目标证据，latest API 不自动适用于厂商旧树。

`AI-02` 必须：先识别受影响接口与不变量，再做最小必要实现。不要引入无需求的 RTOS、万能 HAL、新依赖、协议重构或整个构建迁移；发现重大设计问题时说明证据与可实施修复范围，不擅自扩大任务。

`AI-03` 必须：开发和只读审阅使用不同完成条件。审阅只报告问题；用户授权应用建议后再实施同范围修复。新增项目规范只在任务要求时合并，不自动覆盖用户的 `AGENTS.md`。

`AI-04` 必须：先复用原检查，再补改变行为所需的边界验证。测试应能捕获真实故障：坏长度导致越界、取消导致 UAF、未知 tag 误读等；不要写只核对函数名、注释或实现结构的测试。

`AI-05` 必须：保留原始证据与真实失败。工具不可用、交叉编译缺 sysroot、板卡未连接时报告未执行；不能用模拟输出冒充实机。安全敏感硬件动作在已有任务授权范围内执行，源码开发授权不自动包含烧录/执行器动作。

## 四类任务的输出

| 请求 | 合适的交付 |
| --- | --- |
| 设计新模块 | profile、依赖方向、接口/状态、所有权、预算、恢复策略、测试验收；必要时给头文件草案 |
| 实现功能 | 最小改动、错误/取消路径、必要测试、真实构建结果与未验证硬件项 |
| 审阅代码 | 按后果排序的定位发现，触发条件和修复建议；无证据的担忧不当已确认缺陷 |
| 排查不稳定 | 现象/复现、观测证据、可证伪假设、最小实验、根因修复及回归；不先加延时/volatile 碰运气 |

审阅建议严重度：P0 已证实危及安全/系统不可用且需立即处理；P1 可信路径的数据破坏、内存错误或严重失效；P2 有条件触发的功能/可维护性缺陷；P3 局部风格建议。严重度依据实际路径与影响，不把全部违反规范项都列为 P1。

## 可直接使用的提示

开发：`使用 $embedded-reliability。读取项目证据，识别各组件 profile，按现有架构实现【功能】。对外接口先确定所有权、上下文、超时和错误；核实目标 SDK/API，不猜硬件参数。完成相关检查，区分宿主、交叉和实机结果。`

审阅：`使用 $embedded-reliability，只读审阅【目录或 diff】。重点检查驱动生命周期、指针/长度、异步寿命、DMA/锁、协议布局。按真实风险排序，给文件行号、触发条件、规则 ID、后果、建议和验证办法；不要修改文件。`

排障：`使用 $embedded-reliability，排查【现象】。先记录平台、复现条件和观测，区分硬件时序、资源寿命、并发和协议假设；提出可证伪实验，先做已授权且不依赖硬件的检查。修复需由证据支持。`

生成项目规则：`使用 $embedded-reliability，基于仓库生成适用的嵌入式规范。保留既有 AGENTS/工具链约定，给 kernel/user/MCU 不同 profile，只引入可执行的规则和检查，列出需项目确定的参数。`

## 应用技能本身的限制

技能是决策与验证流程，不是可证明无缺陷的保证。只读材料也可能过时；目标手册/头文件、编译器行为和正式项目约束优先于通用建议。平台规则冲突先定位适用范围；真正冲突不能靠沉默忽略，应记录取舍，必要时提问。
