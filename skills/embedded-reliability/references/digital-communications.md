# 数字信号与通信

先区分物理电气层、控制器/总线驱动、传输、组帧和业务协议。软件 CRC 不能修复电平、终端、地参考或时序问题；通信通了也不能证明所有边界可靠。

## 信号约束

`SIG-01` 必须：确认 I/O 电压、输入容限、推挽/开漏、上拉/下拉、有效极性、复位态、上电先后和跨电源域反灌风险。速率上限要核对连线、负载、边沿、setup/hold、抖动、收发器传播延迟及器件手册；不能仅凭“支持 10MHz”决定板级速率。

`SIG-02` 必须：异步外部 GPIO、机械触点或跨时钟域信号需相应硬件同步/捕获与软件去抖/滤波策略。去抖不能消除硬件亚稳态；纳秒级毛刺不能用慢线程轮询可靠识别。逻辑分析仪看逻辑时序，示波器用于电平/振铃/上升沿，不能互相完全替代。

## 各接口的最小契约

| 接口 | 配置/电气核验 | 软件失效处理与验证 |
| --- | --- | --- |
| UART | 波特率、数据/校验/停止位、流控、电平标准；TTL UART ≠ RS-232 | framing/parity/overrun、半帧/粘帧、收发缓冲上限；idle 事件不自动等于业务帧 |
| RS-485 | 半/全双工、DE/RE 极性、总线拓扑、终端/偏置、共模与隔离 | 最后停止位真正发完再释放 DE，不能把 DMA 搬完当线已空闲；周转、冲突、超时 |
| I²C | 7/10 位地址与 API 表示、开漏/上拉、电容、速率、clock stretch、repeated START | 区分 NACK、仲裁丢失、超时、卡线；按控制器/总线恢复接口处理，不在共享总线上随意手动翻 GPIO |
| SPI | CPOL/CPHA、bit order、word size、速率、CS 极性/时序、dummy 周期 | 保持命令+响应所需 CS 连续性，确认读命令延迟；全双工 RX 不自动意味所有字节有效 |
| CAN/CAN FD | nominal/data bitrate、sample point、终端、控制器/收发器 FD 能力 | 验证 ID/flag、DLC 与实际字节长度、bus-off、错误帧、过滤和恢复；不把 FD DLC 当字节数 |
| TCP | 会话、连接/读写截止期、keepalive 策略 | 字节流需要显式组帧；短读写、半关闭、重连、旧请求完成；不能按单次 recv 划帧 |
| UDP | MTU/分片、最大 datagram、地址与身份策略 | 保留报文边界，处理截断/乱序/重复/丢失；不套 TCP 补齐循环 |

I²C 依据 [NXP UM10204 Rev.7](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)；SPI 依据目标器件和 [Linux SPI](https://docs.kernel.org/driver-api/spi.html)；CAN 依据控制器手册和 [SocketCAN](https://docs.kernel.org/networking/can.html)。RS-485 的电气、终端和偏置需结合具体网络计算，[TI Design Guide](https://www.ti.com/lit/an/slla272d/slla272d.pdf) 提供设计依据；不统一硬套阻值或只按波特率判断是否需要终端。

`BUS-01` 必须：优先使用系统已有控制器驱动/SDK。Linux I²C 用户态组合事务用目标支持的 `I2C_RDWR` 等接口并检查能力；两次 read/write 不保证 repeated START。不得与已绑定驱动竞争访问同一器件；扫描工具也可能对设备有副作用。[I²C userspace interface](https://docs.kernel.org/i2c/dev-interface.html)

`BUS-02` 必须：超时/重试基于事务语义。读取 FIFO、read-clear、触发转换、写执行命令可能有副作用；失败可能意味着“已执行但未收到确认”。仅幂等或有去重方案的操作自动重试，限制总时间与次数，恢复过程不能破坏其他总线设备。

## 帧和解析器

`PRO-01` 必须：定义字段顺序、宽度/符号/端序、版本/类型、长度含义、最大负载、校验覆盖区间、转义、同步与超时。长度字段先范围验证，再分配/访问；避免整数溢出；检查截断、尾随字节、未知版本/类型、保留字段和值域。

`PRO-02` 必须：流解析器区分 need-more、完整帧与错误。错误后有界重同步；不能一遇坏长度无限等待，也不能无限缓存。解析和业务执行分开，验证成功前不改变外部设备状态。输出采用成功后提交或明确的部分结果语义。

`PRO-03` 必须：CRC 记录多项式、初值、输入/输出反射、xorout、处理字节序、覆盖区间和黄金向量。CRC 检测偶发差错，不能提供身份认证；存在恶意修改/重放威胁时使用适当认证与抗重放机制，不靠“加长 CRC”。

`PRO-04` 必须：请求/应答定义序号、重复抑制、复位代次和幂等性；重连后晚到应答不能匹配到新会话。序号回绕、广播、超时完成、取消和重复回调需测试。重试不能造成重复加热、转动或写配置。

`PRO-05` 必须：标准协议按目标版本实现；自创示例不得冒充 Modbus、CANopen 等。Modbus RTU 的帧间隔和 CRC 按协议文档，不与任意 UART idle 时间或示例 CRC 混用。需要实现某个具体协议时补查其官方规范及勘误。

## 证据

保存标注采样率/阈值/探针位置的波形、逻辑解码、帧字节和时间戳；软件测试覆盖每个截断长度、坏长度、bad CRC、未知字段、随机输入、连接中断、bus-off/卡线以及恢复预算。实机测试只能在设备额定条件与已授权的测试范围内进行。

可运行的 [示例编解码器](../assets/examples/frame_codec.c) 仅演示固定格式和本地数据模型的分离，既不是流重同步器，也不是业务协议或网络安全方案。
